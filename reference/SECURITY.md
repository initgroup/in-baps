# IN-BAPS 보안 경계

> 초기 실험판의 보안 검토 이력입니다. 체험 로그인·기존 스키마·배포 상태 설명은 당시 기록이며 현재 적용 지침이 아닙니다. 현재 회원·세션 만료·TARGET 암호화·SQL 경계는 [REAL_DATABASE.md](architecture/REAL_DATABASE.md)와 [AGENTS.md](../AGENTS.md)를 따릅니다.

초기 구현의 실제 보안 기능과 운영 조건을 기록한다. 기존 프로젝트의 [환경·구조 조사](INBUPS_RESEARCH.md) 중 서버 세션과 DB 권한 원칙을 반영했다.

## 인증·권한

- 세션은 무작위 토큰을 발급하고 DB에는 SHA-256 해시만 저장한다. 쿠키는 HttpOnly·SameSite=Lax이며 운영은 Secure를 강제한다. 유효기간은 8시간이고 로그아웃 시 DB 세션을 삭제한다.
- 비밀번호는 무작위 salt와 PBKDF2-HMAC-SHA256 310,000회로 저장한다. 평문이나 복호화 가능한 비밀번호를 저장하지 않는다.
- 모든 업무 API는 DB 세션을 확인한다. 계정·권한을 `localStorage`, 사용자 헤더, URL 또는 요청 본문으로 결정하지 않는다.
- 데이터 조회·분석·시각화는 서버가 결정한 `OWNER_ID`로 제한한다. 다른 소유자의 ID는 404를 반환한다.
- 시스템 상태는 서버의 관리자 검사를 요구한다. 프론트 메뉴 숨김과 별개의 경계다.
- 변경 요청은 DB 세션에 연결된 CSRF 토큰을 요구한다. 로그인·체험 진입은 Origin을 검증하며 IP별 5분 12회 제한을 둔다. 프록시 뒤에서 앱이 HTTP로 요청을 받아도 브라우저 HTTPS Origin을 확인할 수 있도록 `BAPS_PUBLIC_ORIGIN`의 정확한 단일 출처를 추가 허용한다. 미설정 시 Render의 `RENDER_EXTERNAL_HOSTNAME`으로 HTTPS 출처를 구성한다. 임의 하위 도메인·와일드카드는 허용하지 않는다. 이 로그인 제한은 프로세스 메모리이므로 다중 인스턴스 공통 제한을 대체하지 않는다.

체험 로그인은 development·SQLite·루프백 조건에서만 허용한다. 로컬 체험 계정은 시연을 위한 관리자이며 운영 계정으로 사용하지 않는다. `BAPS_ADMIN_PASSWORD`는 12자 이상일 때 최초 관리자 생성에 사용한다. 계정이 이미 있으면 환경변수를 변경해도 저장된 비밀번호를 덮어쓰지 않는다. 초기 버전에는 MFA·비밀번호 재설정 UI·공유 조직/RBAC 세분화가 없다.

## 입력과 실행

- 요청 본문은 Content-Length 유무와 무관하게 크기를 제한한다. multipart 여유 공간을 포함한 요청 제한과 실제 파일 10MiB 제한을 각각 적용한다.
- 행 20,000개, 컬럼 100개, 셀 10,000자 제한이 있다. 중첩 JSON 객체·무한대·NaN·중복 CSV 헤더를 거부한다.
- SQL은 파일에서 읽고 바인드 변수로 실행한다. 임의 SQL 워크시트·PL/SQL 실행·원격 URL 요청 엔드포인트는 제공하지 않는다.
- CSV 내보내기는 수식으로 해석될 수 있는 문자열을 보호한다. 사용자 HTML을 코드로 실행하는 기능은 없다.
- 분석은 숫자 변환과 결측 정책을 명시한다. 텍스트 분석은 입력 텍스트를 코드로 실행하지 않는다.
- 외부 오류·DB 접속 문자열·비밀정보를 클라이언트에 반환하지 않는다. 서버 로그에도 일반 오류 유형을 기록하며 원문 예외를 그대로 노출하지 않는다.

## 웹·비밀정보

정적 마운트는 `frontend/`에 한정한다. `backend/`, `database/`, `reference/`, `.env`, wallet, 런타임 데이터는 정적 URL로 제공하지 않는다. 허용 호스트 검증과 CSP, nosniff, 프레임 차단, Referrer-Policy를 사용한다. 차트 동적 스타일을 위해 CSP의 inline style은 허용하지만 inline script는 허용하지 않는다.

`.env`와 `secrets/oracle/`는 로컬 비밀 자료다. 기존 프로젝트의 환경을 복사하더라도 그 값을 문서·터미널 출력·브라우저·Git에 넣지 않는다. 기존 `INIT_*` 변수가 파일에 남아 있다는 사실만으로 새 앱이 그 인증체계와 연계된 것으로 간주하지 않는다. 새 세션 쿠키 이름과 테이블은 별도다.

프론트 라이브러리는 버전 고정 후 로컬 자산으로 제공한다. 원본 이미지와 조사 파일은 `reference/`에 보관하며 실제 업무 데이터로 표시하지 않는다.

## Oracle와 배포

Oracle 스키마는 앱 시작 시 자동 생성하지 않는다. `backend.migrate apply --schema 대상스키마`가 확인된 대상에만 버전 파일을 적용한다. 적용 이력이 있는 SQL은 체크섬으로 변경을 감지한다. 각 버전은 실행 전 `RUNNING`을 커밋하고 성공 후 `APPLIED`로 바꾼다. 중간 실패 시 일부 DDL이 자동 커밋될 수 있으며, `RUNNING` 이력 또는 최초 설치의 미추적 `INBAPS_*`가 남으면 재실행을 중단해 검토하도록 한다.

운영 전용 스키마와 필요한 최소 권한을 사용한다. 기존 DB 접속 설정을 그대로 참조해도 기존 `INIT$_*`를 읽거나 변경하지 않는다. wallet과 Oracle 관리 권한은 계정·네트워크 환경에 맞게 별도 관리해야 한다.

Render는 별도 IN-BAPS 서비스에 `BAPS_ENV=production`, `BAPS_COOKIE_SECURE=true`, 실제 호스트, 새 관리자 비밀번호, Oracle 비밀 환경변수·Secret Files를 설정한다. Git 원격·Render 서비스는 아직 지정하지 않았고 공개 배포 검증도 수행하지 않았다.

소스 백업은 `.env`·wallet을 제외한다. `-IncludeData` 백업에는 SQLite 사용자·세션·업무 데이터가 포함되므로 비공개로 보관한다. Oracle 구조 내보내기는 데이터 백업이 아니며 Data Pump 또는 DB의 복구 정책이 별도로 필요하다.

## 검증과 남은 범위

오프라인 테스트는 인증 실패, CSRF·Origin, 타 사용자 데이터 접근, 위조 관리자 헤더, 모듈 독립성, 입력 검증을 확인한다. 이는 보안 침투검사나 Oracle·Render 운영환경 검증을 대신하지 않는다. 외부 수집 어댑터, 비밀정보 저장 기능, 다중 테넌트 공유, 장기 감사 로그를 추가하면 해당 경계를 별도로 설계·검증한다.
